# План итогового проекта: ETL грейдера → PostgreSQL

Цель для проверяющего: один понятный pipeline **API → валидация → PostgreSQL → лог**, без лишней архитектуры. Человек должен открыть папку, прочитать README, запустить скрипт и увидеть: логи, таблицу с данными и отсутствие «магии».

Репозиторий на старте пустой — реализация с нуля.

---

## Этап 0. Подготовка окружения

1. Локальный PostgreSQL, которым уже пользуетесь (DBeaver) — Docker не нужен.
2. БД `grader_stats` (создать в DBeaver); в `.env` — те же host/port/user/password, что в подключении DBeaver.
3. Виртуальное окружение Python + зависимости: `requests`, `psycopg2-binary` (или `psycopg2`), при необходимости `python-dotenv`.
4. `.env` / конфиг для пароля БД и ключей API — **не** коммитить секреты; в README — пример `.env.example`.
5. Структура проекта:

```text
simulative-final/
├── main.py              # точка входа
├── config.py            # URL, client, ключи, путь к логам, DSN
├── api_client.py        # запрос к API
├── transform.py         # разбор passback_params + валидация
├── db.py                # создание таблицы, insert
├── logging_setup.py     # логи + ротация за 3 дня
├── requirements.txt
├── .env.example
├── README.md            # как поднять БД и запустить
└── logs/                # лог-файлы по дате
```

Для учебного проекта допустим и один `main.py`, но разбиение проще читать человеку.

## Этап 1. Логирование (сделать первым)

Чтобы каждый следующий шаг уже писал стадии в файл.

1. Папка `logs/`.
2. Имя файла: `YYYY-MM-DD.log` (или с временем, если запускают несколько раз в день — но по ТЗ достаточно даты).
3. `logging.basicConfig` / `FileHandler` + формат с **временной меткой**, уровнем и сообщением.
4. При старте: удалить логи старше **3 дней**.
5. Сразу заложить сообщения уровней INFO/ERROR под весь pipeline (скачивание, обработка, загрузка в БД).

Проверяющий откроет лог и увидит хронологию — это сильный плюс.

## Этап 3. Разбор и валидация `passback_params`

Это ядро задания — здесь чаще всего «сыпятся» решения.

1. Исходный вид — строка, похожая на `repr` словаря Python (`'...'` внутри).
2. Безопасный разбор: `ast.literal_eval` (не `eval`). Fallback: аккуратная нормализация кавычек + `json.loads`, если понадобится.
3. Маппинг в целевые поля:

| Поле БД | Источник |
|---------|----------|
| `user_id` | `lti_user_id` |
| `oauth_consumer_key` | из `passback_params` |
| `lis_result_sourcedid` | из `passback_params` |
| `lis_outcome_service_url` | из `passback_params` |
| `is_correct` | из ответа (`null`/`True`/`False`) |
| `attempt_type` | `run` / `submit` (и др., если встретятся) |
| `created_at` | дата-время попытки |

4. Валидация по каждой записи:
   - обязательные поля не пустые (кроме допустимого `is_correct is null` для `run`);
   - типы: строки / bool|None / datetime;
   - `created_at` парсится в datetime;
   - лишние ключи в `passback_params` игнорируем, отсутствующие обязательные → skip.
5. Битую запись **пропускаем**, пишем в лог WARNING/ERROR с причиной (и при возможности — `user_id` / индекс).
6. INFO: сколько принято / сколько отброшено.

## Этап 4. Схема PostgreSQL и загрузка

1. DDL таблицы, например `attempts` / `grader_statistics`, типы:
   - `user_id` TEXT
   - `oauth_consumer_key` TEXT
   - `lis_result_sourcedid` TEXT
   - `lis_outcome_service_url` TEXT
   - `is_correct` BOOLEAN NULL
   - `attempt_type` TEXT
   - `created_at` TIMESTAMP
2. При старте: `CREATE TABLE IF NOT EXISTS`.
3. Вставка через `psycopg2` + `executemany` / `execute_batch` (для объёма).
4. Стратегия повторных запусков (явно описать в README):
   - либо truncate + полная перезаливка за период;
   - либо уникальный ключ + `ON CONFLICT DO NOTHING` (если есть естественный ключ; если нет — хотя бы документировать поведение).
5. Транзакция: успех → commit; ошибка БД → rollback + ERROR в лог.
6. INFO: «заполнение БД началось/завершилось, N строк».

## Этап 5. Сборка pipeline в `main`

Порядок в одном прогоне:

1. Настроить лог + очистка старых логов
2. Подключиться к БД / убедиться, что таблица есть
3. Скачать данные за `start`–`end`
4. Преобразовать и провалидировать
5. Загрузить в PostgreSQL
6. Итоговый INFO-summary (скачано / валидно / загружено / ошибок)

Обернуть топ-уровень в `try/except`, чтобы необработанные исключения тоже попали в лог.

## Этап 7. Самопроверка перед сдачей

1. Короткий диапазон дат → скрипт отрабатывает end-to-end.
2. Лог: стадии + хотя бы одна намеренно/естественно отбракованная запись (если API даёт мусор).
3. В папке логов только файлы за ≤3 дней.
4. Повторный запуск не ломает БД (по выбранной стратегии).
5. Ключи и пароли не в git.
6. Код читаемый: понятные имена, без мёртвого кода, комментарии только где неочевидно (`passback_params`).

## Принципы решений

- **Простота важнее «фреймворков»** — это учебный ETL, не микросервис.
- **Явные логи стадий** — проверяющий смотрит файл, а не только stdout.
- **Жёсткая валидация с skip** — битая запись не валит весь скрипт.
- **Воспроизводимый запуск** — даты и доступы снаружи, не захардкожены в середине кода.
